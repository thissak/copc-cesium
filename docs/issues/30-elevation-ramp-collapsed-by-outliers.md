## 1. 문제

### 증상
- RGB 차원이 없는 COPC(SoFi Stadium 1.9GB)를 열면 점군 전체가 **형광 초록 단색**으로 렌더된다.
- 지형·건물의 높이 차가 전혀 보이지 않아 3D 점군이 평평한 색면처럼 보인다.
- RGB 가 있는 Autzen 은 정상이므로 **RGB 없는 데이터셋에서만** 드러난다.

### 재현 조건
- 환경: Windows 11, Chromium 149 (Playwright 1228), RTX 4090, 1920×1080
- 단계:
  1. `npm run dev`
  2. `http://localhost:5173/?ds=sofi`
  3. 로드 완료 후 색 분포 확인 → 전 구역 동일한 초록

### 스크린샷 / 로그
- 출품 영상 촬영 중 발견. **주의**: `assets/raw/sofi-orbit.mp4` 는 수정 후 재촬영되어 현재 파일에는
  이 증상이 없다(램프 정상). 증상 재현은 `scripts/bench/repro-30.ts` 를 수정 전 코드에서 돌려 확인한다.
- 콘솔: `[copc] colorBy 'rgb' 차원 없음 → height 폴백`

## 2. 원인 분석

### 측정 데이터

`copc.js` 로 두 데이터셋의 차원과 Z 분포를 직접 확인:

| | Autzen | SoFi |
|---|---|---|
| RGB 차원 | **있음** (16-bit, 최대 54272) | **없음** |
| header Z (min..max) | 406.14 .. 615.26 (span 209m) | **-83.709 .. 138.186** (span 222m) |
| 루트 노드 실제 점 Z | 406.7 .. 615.3 | **-83.7 .. 51.0** |
| header 범위로 정규화한 t | 0.003 .. 1.000 (**전 구간 사용**) | 0.000 .. 0.607 |

SoFi 는 미 LA 이며 실제 지반고가 약 30m 다. header 최소값 **-83.7m** 는 지형이 아니라 **노이즈 점**이다.

색 램프는 `hslToRgb((1 - t) * 0.66, …)` 이므로 t≈0.5 → hue≈0.33 = **초록**.
실제 지형(≈30m)의 t = (30 + 83.7) / 222 ≈ **0.51** → 지형 전체가 초록 한 지점에 몰린다.

### 근본 원인

`src/copc-core.ts:762`

```ts
const zRange: [number, number] = [s.copc.header.min[2] * s.zUnit, s.copc.header.max[2] * s.zUnit];
```

고도색을 **LAS header 의 원시 min/max** 로 정규화한다. 노드 간 색 일관성을 위해 전역 범위를 쓰는 것
자체는 옳다(Potree elevationRange 방식). 문제는 그 전역 범위가 **이상치에 무방비**라는 점이다.
바닥/천장에 노이즈가 몇 점만 있어도 램프 전체가 그 점들에 끌려가 실제 지형은 좁은 색 구간으로 압축된다.

관련: 플러그인은 기본적으로 classification 7·18(노이즈)을 **렌더에서 숨기지만**(`hideClassifications`),
**색 범위 계산은 여전히 그 점들을 포함한 header 값을 쓴다.** 숨긴 점이 색을 지배하는 모순.

## 3. Best Practice 조사

### 조사 항목
- Cesium 공식 레퍼런스에 색 램프 범위 정책이 규정돼 있는지.
- 데이터 자체에서 이상치를 식별할 수 있는지(분류 코드 등).
- 노드 간 색 일관성을 유지하면서 이상치만 배제하는 방법.

### 프로덕션 사례
| 프로젝트 | 접근 방식 | 비고 |
|---------|----------|------|
| CesiumJS `Cesium3DTileStyle` | 색은 **표현식**(`conditions`, `${Classification}`, `${height}`)으로만 규정. 램프 범위 정책은 **정의하지 않음** | [ref-doc/Cesium3DTileStyle](https://cesium.com/learn/cesiumjs/ref-doc/Cesium3DTileStyle.html) — 범위 결정은 데이터 제공자 몫 |
| Potree elevationRange | 노드별이 아닌 **데이터셋 전역** 범위로 정규화해 노드 간 색을 일관되게 | 본 프로젝트가 이미 채택한 방식(`colorize` 주석) — 전역이라는 성질은 유지해야 함 |
| ASPRS 분류 코드 | 7 = Low Point(noise), 18 = High Noise | 본 프로젝트도 기본 `hideClassifications: [7, 18]` |

**분류 기반 필터가 답이 아님을 측정으로 확인**: SoFi 루트 노드의 노이즈 분류 점은 **0개**인데도
-83.7m 이상치가 존재한다. 즉 이상치가 항상 분류돼 있지 않으므로 **값 기반(백분위) 클리핑**이 필요하다.
(반대로 millsite 는 루트 72,406점 중 31,871점이 노이즈 분류 — 데이터마다 편차가 크다.)

Cesium 공식이 규정하지 않는 영역이므로, **전역 일관성(Potree 방식)은 유지하면서 범위 산출만 이상치에
강건하게** 바꾸는 것이 이 프로젝트의 결정이다.

### 엣지 케이스 / 위험 요소
| 시나리오 | 위험도 | 대응 |
|---------|--------|------|
| 노드 간 색 불일치 | 높 | 범위는 반드시 **세션 전역 1회** 계산해야 함. 노드별 계산 금지 |
| 실제로 고도차가 큰 데이터(산악·고층) | 중 | 클리핑이 정상 지형을 잘라 포화되면 안 됨 |
| 수직형 스캔(벽면) | 중 | Z 분포가 균일하지 않아도 동작해야 함 |
| 범위 계산 비용 | 중 | 전체 점을 읽으면 대형 파일에서 비쌈 — 샘플링 필요 |

## 4. 수정 내용

### 변경 파일
| 파일 | 변경 요약 |
|------|----------|
| `src/copc-core.ts` | `CopcSession.rampZRange`/`rampZPending` 추가. `percentileRange()`·`ensureRampZRange()` 신설. `colorize` 가 header 원시 min/max 대신 클리핑 범위 사용 |
| `scripts/bench/repro-30.ts` | 재현·검증 스크립트 (신규) |

**표본 출처**: COPC **루트 노드**. 옥트리 루트는 전 범위를 고르게 훑는 부분표본이라 전역 분포의 대리로 적합하다.
루트를 디코드하는 중이면 그 `zVals` 를 그대로 써 **추가 요청이 없다**. 세션당 1회(single-flight)만 계산해
노드 간 색 일관성을 지킨다. 실패하면 조용히 header 범위로 폴백해 렌더를 막지 않는다.
램프를 실제로 쓰는 경우(=`height` 이거나 요청 차원이 없어 폴백)에만 계산하므로 RGB 데이터셋은 무영향.

### Before / After
```typescript
// Before — 이상치 몇 점이 램프 전체를 지배
const zRange: [number, number] = [s.copc.header.min[2] * s.zUnit, s.copc.header.max[2] * s.zUnit];

// After — 루트 노드 Z 의 1–99% 백분위. 실패 시에만 header 폴백.
const zRange: [number, number] =
  s.rampZRange ?? [s.copc.header.min[2] * s.zUnit, s.copc.header.max[2] * s.zUnit];
```

### PR
(브랜치 `fix/28-zoomto-frames-octree-cube` 에 동승 — 파일이 겹치지 않아 커밋 분리 가능)

## 5. 검증 결과

### 테스트 방법
`scripts/bench/repro-30.ts` — dev 서버 기동 후 `tsx scripts/bench/repro-30.ts [ds]`.

배경(지구본·하늘·태양)과 DOM 오버레이를 끈 캔버스에서 점군 픽셀의 **색상(hue) 분포**를 잰다.
판정 지표는 색상환에서 유채색 픽셀의 **90% 를 덮는 최소 호(arc) 길이**.
- 합격: hue 스팬 ≥ 90° (정상 램프는 파랑 238° → 빨강 0° 를 훑는다)

> 기각한 1차 지표: "쓰인 hue 버킷 수(≥2%)". 전부 초록이어도 인접 버킷 7개가 잡혀 **오탐 PASS** 가 났다.
> 뭉침을 재려면 개수가 아니라 **퍼진 폭**을 재야 한다.

### 잔여 이슈
- 백분위를 **루트 노드 표본**에서 잡으므로, 깊은 LOD 에만 존재하는 극단 고도(예: 루트에 안 잡힌 첨탑)는
  램프 양 끝에서 포화된다. 색 램프의 통상적 거동이며 단색 붕괴보다 훨씬 낫다. 필요해지면 옵션으로 노출한다.
- 클리핑 백분위(1–99%)는 현재 상수다. 데이터별 조정이 필요해지면 `CopcTilesetOptions` 로 뺀다.
